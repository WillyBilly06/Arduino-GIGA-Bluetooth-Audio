# Dev.11 transport option and coexistence observations

This is an experimental development source. Earlier audio shortages have no demonstrated root-cause fix, and clock-deadline failures remain. These observations do not qualify every codec, the public default buffers, physical audio continuity, numerical fidelity, or the requested 200 ms total phone-to-DAC latency.

## Public source build

The public source was frozen before compilation. Official Arduino Mbed GIGA Boards 4.6.0 / ARM GCC 7-2017q4 compiled Receiver for Cortex-M7 in 107.203 seconds, exit 0, with the compiler job quiescent and source/SDK response files unchanged. The build selected the project host, controller UART 3000000, WS D74 and private scheduling witness 0. It retained 170 library translation units, all six decoder-operation families and all seven codec defaults. No historical BTstack host was linked. The stock 35,182-byte / 139-command HCD is unchanged.

BIN SHA256: `ff8078ce6a10d7948f159e3b7a8cfdcf89825f47a929f4c9bf1dd4f15bd0c9d5` (497,008 bytes).

ELF SHA256: `725219cca80156f5cc3d6a5dde454139f1dc891ade813a312aaae1f78aeb86f3`.

The linked audit verified ARM/softfp attributes, vector bounds, the 32 KiB main stack, flash LOAD-to-BIN correspondence, selected host symbols, codec callback addresses, and exact HCD identity. The compile-time baud-policy checks passed using the official ARM compiler; the same test without its helper failed as expected. OwnedHost and OwnedRadio also compiled as ARM objects at unchanged default 2 Mbaud. That is not a new full default-2-Mbaud link or an execution of the Windows native test suite. The public image was not flashed.

The [machine-readable evidence](dev11-2026-10-27.json) identifies the frozen code projection and artifacts. Later documentation-only packaging is verified against every source/Receiver input; its final ZIP identity is external to the ZIP. Historical BUILD.json remains dev.10 and earlier evidence.

## Different private field image

A separately identified private image used the same supported 3 Mbaud option with an 80 ms LHDC startup / 90 ms PCM ring override and private scheduling/receive observers. Its BIN SHA256 is `de560fd24113a6d74e454c8631284d72f85fad1df5afe144d126dde939f898d0` (512,904 bytes). Its full image was written and readback verified before testing.

The 600-second ordinary-source LHDC V5 192,000 Hz / 24-bit test, with the phone's fixed 1000 kbps setting requested, retained 598.088 seconds of printed telemetry. Three BLE reconnect/data cycles completed 46, 44 and 45 verified 512-byte GATT exchanges at negotiated MTU 517. During that bounded window, recorded missing PCM, underruns, decode/transport/DMA errors, RTP outer/timestamp/codec-sequence discontinuities and compressed-queue overflows were zero. Real decoded-frame progress was observed; this was not an idle-window result. Closing a phone client alone is not proof of physical BLE detachment.

Clock CUM still recorded 19 deadline overruns. Private observer accounting was 1,322 bytes against the original 1,024-byte gate, so that gate failed. Neither failure is waived. UART registers showed BRR 40, prescaler code 0 and 16-times oversampling, with successful post-switch HCI and profile traffic. The kernel-frequency getter returned zero, meaning UNKNOWN/unsupported; nominal 3 Mbaud relies on a separate conditional 120 MHz kernel model, not an independent frequency measurement.

This is one finite operating window, not a controlled causal comparison with 2 Mbaud, a physical headphone test, a latency measurement or a stable-library qualification. Public automatic buffer geometry differs, so its audio behavior cannot be inferred from this private image.

## ACK, retransmission and coexistence boundary

BR/EDR ACL error recovery uses controller/baseband ARQ. The host's HCI completed-packet flow-control messages release buffers; they are not over-air ACKs or RTP retransmission requests. Increasing host queues does not itself command radio retransmissions. The [Bluetooth baseband specification](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/Core-54/out/en/br-edr-controller/baseband-specification.html) describes this distinction. No guessed coexistence opcode or firmware patch is added here.

The option retains the existing UART baud-change sequence; [Infineon's documented example](https://community.infineon.com/t5/Knowledge-Base-Articles/Using-Vendor-Specific-Commands-in-AnyCloud-Bluetooth-Applications/ta-p/267534) uses 3 Mbaud and completes the command at the old baud before the switch. For 649 bytes with 8N1 framing, nominal wire occupancy falls from 3.245 ms at 2 Mbaud to 2.163 ms at 3 Mbaud. This is a transport-margin calculation, not measured RF retry activity or proof of the earlier gap's origin. Four Mbaud remains rejected by this port.
